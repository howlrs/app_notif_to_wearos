## 1. 使い方

- **要決定（D）**: 関係者の判断が必要な事項。決めたら「決定内容」に記入し、関連する資料を更新する。
- **技術リスク（R）**: OS、Google Play、FCM、現場環境の制約から来るリスク。PoC（[05 §3](05-implementation-plan.md#3-poc-検証項目)）や公式ドキュメントで確かめる。
- 期限の M0〜M6 は [05-implementation-plan.md](05-implementation-plan.md) のマイルストーン。
- Android、Wear OS、Google Play の仕様は 2026 年 10 月時点の情報に基づく。版によって変わるため、実装前に公式ドキュメントで再確認する。
- 2026-10-19 に D はすべて推奨案で決定し、Wear OS 5 エミュレーターと Firebase（business-484010）経由の実送信で検証した。検証で分かったことは「確認結果」として各行に追記した。

## 3. 技術リスク

| ID | リスク | 影響 | 対応 | 確認方法 |
| --- | --- | --- | --- | --- |
| R-01 | Android 14（Wear OS 5）以降、FullScreenIntent は通話・アラーム用途に制限される。確認結果: Wear OS 5 エミュレーターでは権限が付いていてもシステム UI が起動せず（`Fullscreen flag not enabled`）、許可の設定画面もない | 警告画面が自動では開かない | 通知チャンネルに振動を付けて割り込み扱いにし、手首を上げた時（画面点灯時）に警告と「確認」ボタンを表示する。振動・アラーム音で気付かせる運用を前提にする（[02 §5.6](02-wearos-app-spec.md#56-画面点灯と警告の表示)） | P-04（実機で再確認） |
| R-02 | Bluetooth を切った単体運用で、スリープ中やバッテリーセーバー中に Wi-Fi が切れる、または再接続が遅れる可能性がある | 通知が遅れる、届かない | キッティングでバッテリーセーバーの自動オンを無効にする。実機で維持状況を測る | P-01〜P-03、P-12 |
| R-03 | FCM は配信を保証しない。高優先度でも遅延や欠落があり得る | 警告を見逃す | 本システムを補助的な通知手段と位置付け、既存の警報手段と併用する。必要なら ACK で未着を見える化する（D-05） | 現場試行 |
| R-04 | バックグラウンドのアプリからの振動は OS に抑止されることがある | 振動しない | 振動の用途を `USAGE_ALARM` として指定する | P-05 |
| R-05 | 通知チャンネルの重要度・音・振動は、作成後にアプリから変更できない | 更新で設定を変えても反映されない | チャンネル ID に版を付け（`site_alert_v1`）、設定を変える時は新しい ID で作り直して古いチャンネルを削除する | 実装レビュー |
| R-06 | Android 13（Wear OS 4）以降、通知の表示には実行時の許可（`POST_NOTIFICATIONS`）が必要 | 許可しないと通知が出ない | 初回起動時に許可を求め、キッティング手順で確かめる | キッティング |
| R-07 | おやすみモード、ベッドタイムモード、シアターモードで通知が抑止される | 音や振動が出ない | キッティングでオフにする。アラーム用途の音・振動がこれらのモードでどう扱われるかを実機で確かめる | P-06 |
| R-08 | 現場ネットワークが FCM のポート（TCP 5228〜5230）を塞いでいる、ログイン画面付き Wi-Fi である、5GHz のみである | 受信も登録もできない | 現場 Wi-Fi の要件を定め、導入時にテスト通知で確かめる（[04 §4.1](04-operations-runbook.md#41-現場導入時)） | 現場導入時 |
| R-09 | 内部テストのテスターは 100 アカウントまで | 台数を増やせない | D-03 で共通アカウントにする | Play Console |
| R-10 | 自動更新は Play ストアが決めたタイミングで行われ、即時ではない | 新旧のアプリが混在する | 登録 API とペイロードは後方互換を保ち、必須項目を後から増やさない。`app_version` を集計する | P-08 |
| R-11 | 登録 API が無認証だと、第三者が任意の番号のトークンを上書きできる | 警告が別の端末に届く、届かなくなる | D-02 で認証方式を決める | 実装レビュー。D-14 以降は他の時計の行を上書きできないため、届かなくなる被害は防げる。任意の時計を現場に足すことはできる |
| R-22 | 時計の行は、その時計が登録し直すまで残る | 返却して保管中の時計や紛失した時計にも、最後に登録した現場の通知が届き続ける | 紛失・長期保管の時は管理者が `remove` で外す（[04 §5](04-operations-runbook.md#5-端末の番号変更交換紛失補足)）。登録の有効期限は、期限切れで通知が届かなくなる危険があるため設けていない。必要なら現場試行の結果で決める | 現場試行 |
| R-12 | 設定画面から強制停止されたアプリには FCM が届かない（インストール直後も一度起動するまで同じ） | 通知が届かない | キッティングで必ずアプリを開く。強制停止しないよう周知し、トラブルシューティングに載せる | P-11 |
| R-13 | Google Play の `targetSdk` 要件は毎年更新される | 期限を過ぎると新しいバージョンを配信できない | 毎年の対応作業を保守計画に入れる | 年次 |
| R-14 | 高優先度メッセージを受けても通知を表示しないことが続くと、FCM が優先度を下げることがある | スリープ中に届かなくなる | `high` で送るメッセージは、テスト通知も含めて必ず通知として表示する | 実装レビュー |
| R-15 | Wi-Fi を常時接続すると電池の減りが早い | 勤務中に電池が切れる | 毎日の充電を運用に組み込む。実機で 1 勤務分の消費を測る | P-09 |
| R-16 | 内部テストは本来テスト用の配信手段であり、長期の業務配信に使うと Google Play の仕様変更の影響を受けやすい | 配信手段の変更が必要になる | 本格展開時にクローズドテスト（審査あり）や、企業向けの非公開アプリ配信（Wear OS での対応状況は要確認）を比較する | M6 |
| R-17 | `KeyboardType.Number` で数字テンキーだけが出るかは、機種のキーボードアプリに依存する | 文字キーボードが出て入力しにくい | 実機で確かめ、駄目なら Wear OS の `Picker` や独自のテンキー画面に切り替える | P-07（エミュレーターの Gboard では数字だけのテンキーを確認） |
| R-18 | 騒音、手袋、作業中の姿勢で、振動・音・画面表示に気付けない、または「確認」を押しにくい | 警告を見逃す | 警告画面のボタンを大きくし、D-04 で繰り返し鳴動を検討する。実地で確かめる | P-10 |
| R-19 | 単体運用でも、機種によっては一部の設定変更や OS 更新にスマホとの再接続が必要な場合がある | 現場での設定変更に手間がかかる | 機種選定時に確かめ、キッティング手順に反映する | D-08 |
| R-20 | FCM の登録トークン（`getToken` / `onNewToken`、HTTP v1 の `token` 欄）は非推奨になり、Firebase Installation ID（FID）による登録へ移行中 | 原本どおりに作ると、非推奨 API に依存する | FID 方式（`register()` / `onRegistered()`、送信は `fid` 欄）で実装済み。API・DB の項目名 `fcm_token` は残し中身を FID にした | 実装済み |
| R-21 | 開発環境（ExpressVPN 経由）で、VPN の DNS が `fcm.googleapis.com` を解決しなかった。また、長時間アイドルの後に端末と FCM の接続が切れたままになり、配信が遅れた | バックエンドの設置先や現場ネットワークによっては、送信できない・届くのが遅れる | バックエンドの設置先で `fcm.googleapis.com` の名前解決と HTTPS 到達を確認する。現場 Wi-Fi・実機で長時間待機後の到達時間を測る（P-02、P-03） | 現場導入前 |

## 4. 原本内の不整合と解釈

| No. | 箇所 | 内容 | 本資料での扱い |
| --- | --- | --- | --- |
| 1 | §2 ③ と「次のアクション」 | 振動を「1 秒振動＋0.5 秒休止 × 5 回」（約 7 秒）とする記述と、プロンプト例の「5 秒間」が食い違う | 仕様本文（約 7 秒）を正とし、定数で変えられるようにする |
| 2 | §2 ③ | 「重要度を最大（`IMPORTANCE_HIGH`）」とある。API には `IMPORTANCE_MAX` もあるが使われていない値であり、アプリが実際に使える最大値は `IMPORTANCE_HIGH` | 原本どおり `IMPORTANCE_HIGH` とする |
| 3 | §2 ③ | 画面点灯の手段として「WakeLock / FullScreenIntent」が並記されている | FullScreenIntent を基本とし、WakeLock は CPU 維持に使う。画面点灯用の WakeLock は PoC で必要と分かった場合の予備とする（[02 §5.6](02-wearos-app-spec.md#56-画面点灯と警告の表示)） |
| 4 | §2 ② | トークンの再登録は「アプリ起動時」のみ | 宛先 ID が変わった時に呼ばれる `onRegistered()` でも再登録する（[02 §4.3](02-wearos-app-spec.md#43-送信タイミング)） |
| 5 | §2 ② | `FirebaseMessaging.getInstance().token` でトークンを取得 | 非推奨のため FID 方式に変更（R-20） |
